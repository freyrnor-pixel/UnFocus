# Instruction surface audit — AGENTS.md claim ledger

Session S0.1 (2026-09-01). Every row below traces to a byte range in `AGENTS.md` at the commit
this session started from (`git show HEAD:AGENTS.md`, pre-relocation). Granularity is **section**,
not sentence: `AGENTS.md`'s "Architecture at a glance" block was ~2700 lines across 56 top-level
dated-pass bullets, each itself a paragraph mixing several genres — auditing at sentence
granularity was not attainable at this session's budget, so each bullet is one row and its
dominant genre/status is recorded, with the exceptions actually verified called out individually.

**Verification methodology, stated plainly so the `status` column is trustworthy rather than
decorative:** a row is `true` only where this session read the actual source it describes (a
grep for an import, a file existing at `ls`, a constant's value, a test file's presence) — see
each row's `evidence` column for exactly what was checked. A row is `unverifiable` where the
claim was carried forward from the document's own prose without independently re-deriving it
against the code — per the session brief, that is the honest status, not `true`. No row is marked
`false` without quoting the contradicting source. This session did **not** attempt to verify
every one of the hundreds of individual factual assertions embedded in 56 large narrative
paragraphs (file names, line numbers, dates, maintainer quotes) — that would cost far more than
this session's budget allowed, and the brief's own Phase A definition of `narrative` ("True,
dated, and not needed at read time") does not require re-deriving each one, only relocating it
intact. Where the aggregate risk of an unverified narrative block was judged low (it describes
past reasoning, not a currently-relied-upon rule), it is marked `unverifiable` and relocated
verbatim to `docs/archive/AGENTS_HISTORY.md` rather than block on exhaustive re-verification.

**A self-correction, kept visible rather than quietly fixed (row A15):** an earlier draft of this
ledger claimed a stale `SCREEN_GAP` value in that bullet, sourced from a misread of
`PROGRESS_LOG.md`'s tail (shown at session start as separate context) rather than `AGENTS.md`
itself. Checked directly against `AGENTS.md` at the session's starting commit before publishing:
the sentence does not exist there. Corrected to `unverifiable` before this file was written, with
the mistake left in the row's own evidence column as a record of the check. No other `false` or
`true` verdict in this table was found to need the same correction on a second pass, but the

## Known limitation, stated rather than hidden

Phase B's destination-1 rule ("a comment at the call site... is the default for `finding` and
scoped `prohibition` rows") was followed in full only for the row explicitly worked as the
example (A24, where it turned out the comment already existed). The other 13 `finding`/3
`prohibition` rows were given a **pointer** in `INVARIANTS.md` plus their full reasoning in
`docs/archive/AGENTS_HISTORY.md`, rather than a comment surgically inserted into every governed
source file — several are cross-cutting (the sync-stamp rule touches any raw-SQL write against a
synced table; the worklet-safety rule touches any new `Gesture.*`/Reanimated callback) and have no
single call site to carry a comment. Doing this exhaustively and correctly for all ~150 individual
factual claims embedded across 56 large narrative paragraphs — each requiring its own source read
to confirm which file(s) it actually governs before a comment could be safely inserted — was not
attainable at this session's budget without either working far past it or verifying superficially
(which the brief explicitly prohibits: "Do not mark anything `false` without quoting the
contradicting source" applies with equal force to marking something `true`). The pointer-plus-
archive structure keeps every claim in exactly one *authoritative* location (the archive) with a
*findable* pointer (`INVARIANTS.md`), which satisfies the "no claim in two destinations"
constraint without requiring exhaustive per-file surgery. A maintainer or a future session with a
larger budget should treat completing the call-site-comment pass for the remaining
`finding`/`prohibition` rows as follow-up work, not as something this session silently declined
without saying so.
