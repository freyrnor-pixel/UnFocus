# V3_GAP_2026-09-07.md — the app against `UnFocus_Screens_v3.html`

**Run:** 2026-09-07, at the maintainer's request (*"Have you made it so app looks like mockup?"*).
**Source audited:** `UnFocus_Screens_v3.html`, supplied 2026-09-07. **It is not in the repo** — it
arrived as a session upload and has never existed in git history on any branch. A copy must be
committed before any session can cite it, or every claim below is unverifiable by the next reader.
**Companion:** `DESIGN_GAP_2026-09-06.md` audits the app against the `DESIGN_COMPARISON/` set
(rounds 19–20). That set and this file are **different mockups**, and where they disagree this one
is newer but has not been ruled canonical. See §2.

**Method:** every difference is bucketed — (a) genuinely unbuilt · (b) **conflicts with a shipped
decision** · (c) already absorbed, with a documented deviation · (d) not covered by v3 at all.
Bucket (b) is the important one and it is new: the 09-06 audit had no category for "the mockup
contradicts something that merged this week", because that had not happened yet.

**No code was changed by this audit.** That was the instruction.

---

## Bottom line

**v3 is a good specification of LOOK and a contested specification of STRUCTURE, and the two need
separating before anyone writes code.**

The look half is genuinely well-formed: 18 `color-mix()` expressions, a consistent card anatomy,
and an animation section that gives durations *and* curves *and* the reason for each. The session
prompts written against it (`session-A-tokens.md`, `session-B-anatomy.md`) verify exactly — 18
`color-mix()` occurrences, the radius list `8/9/10/11/12/14/16/20/22/34/99/999`, fifteen font sizes
including half-pixels, and the page-scaffolding values `78/96/100/280/300/372/760/1180`. Whoever
wrote those prompts read this file carefully and counted honestly.

Three things stop it being actionable as-is:

1. **`styles.css` is missing** and it holds every colour. Blocking. §1.
2. **v3's information architecture contradicts five shipped cards**, one of them merged yesterday. §2.
3. **v3's token NAMES collide with the app's at different VALUES** — `Radius.sm/md/lg` in
   particular. Merging them naively restyles the whole app silently. §3.

## 1. Blocking: `styles.css` was not supplied

`UnFocus_Screens_v3.html` line 3:

```html
<link rel="stylesheet" href="styles.css">
```

Measured: the file **consumes 8 CSS custom properties and defines 0 of them.**

| consumed | defines it | needed for |
|---|---|---|
| `--acc`, `--acc2` | `styles.css` | every card accent, the three backdrop washes |
| `--f` | set from `--acc` per card | rows, checkboxes, chips, buttons, the ring |
| `--feature-shop`, `--feature-meals`, `--feature-task`, `--feature-focus`, `--feature-capture`, `--feature-habits`, `--feature-health` | `styles.css` | which hue each of the 12 cards wears |
| `--bubble-ink` | `styles.css` | the ink on every filled control |
| `--font-sans` | `styles.css` (falls back to Nunito) | the type ramp |

**Consequence:** Session A's Task 4 — *"Enumerate every distinct (base colour, percentage, mix
target) triple. Resolve each to a literal hex"* — is impossible. All 18 `color-mix()` expressions
resolve against `var(--acc)` / `var(--f)` / `var(--acc2)` / `var(--feature-health)`, and none of
those four has a value here. Tasks 1–3 (spacing, radius, type) do **not** need it and could run today.

**Not safely substitutable from the repo.** The app has feature hues that look like a match
(`featTask`, `featHabit`, `featHealth`, `featMeal`, `featShop` in `constants/colors.ts`) and does
use Nunito — but `constants/colors.ts` carries **more than one palette generation**, and they
disagree hard: `featTask` is `#2563EB` (blue) in one block and the identity hue for To-do is
`#FFD700` (gold) in another. Picking one would be a guess presented as an extraction. What is
needed is the actual `styles.css` v3 was rendered with.

**Ask:** send `styles.css`. It is the one artefact that unblocks the colour half.

## 2. Bucket (b) — v3 contradicts shipped structure

This is the section that needs a maintainer ruling, not an agent's judgement.

v3 defines exactly **12 cards** across five tabs (extracted from its `card()` calls and its
`S.open` state map). The app's `lib/cardRegistry.ts` defines **15**. They are not the same 12.

### 2.1 Shop — three conflicts on one tab

v3's Handle tab is **three** cards: `lists` (Handlelister), `katalog` (Katalog), `budget`
(Budsjett). The app's is four: `shopLists`, `shopMonthly`, `shopDishes`, `shopCatalogue`.

| # | v3 says | app does | note |
|---|---|---|---|
| S-1 | **Månedsliste is a GROUP inside Handlelister** — `S.lists` is `[{n:'Uke'},{n:'Måned'}]`, both rendered as `.gsec` groups in the one card | `shopMonthly` is a top-level card | ⚠️ **PR #676 merged 2026-09-07 08:44 did the opposite**, titled *"Restore Monthly as a top-level Shop card, matching the Handle mockup"* — citing the OLDER `20-corrected-screens.html`. v3 reverses it, one day later. |
| S-2 | **Retter is a TAB inside Katalog** — `katalog()` draws a `.seg` with Varer/Retter | `shopDishes` is a separate top-level card | Same shape of conflict, not yet litigated. |
| S-3 | **A Budsjett card exists** — amount per week/month, payday reset, two `.bigk` stats (`budsjett ÷ dager`, `brukt ÷ dager siden nullstilling`) | No budget card in the registry at all | Genuinely unbuilt (bucket a), and the largest single piece of new work in v3. |

S-1 is the one to rule on first. It is a direct reversal of work merged yesterday, and whichever
way it goes, one of the two mockups needs to stop being cited.

### 2.2 Home — Energy is absent from v3 entirely

**`grep -i "energi\|energy"` over `UnFocus_Screens_v3.html` returns nothing.**

v3's Hjem is three cards: `notes` (Notater), `htasks` (I dag), `hhabits` (Vaner). The app's Home is
the Energy strip plus `homeToday`, `homeNotes`, `homeShopping`.

| # | v3 says | app does |
|---|---|---|
| H-1 | No Energy strip, no Energy card, no energy anywhere | The Energy strip is Home's first element |
| H-2 | A **Vaner** card on Home (`hhabits`, with the progress rings) | No habits card on Home |
| H-3 | No shopping card on Home | `homeShopping` |

**H-1 matters disproportionately.** The last four merged PRs — #673, #675, #677, #678 — were all
Energy work: the CTA halo, the Energibudsjett bar, the glass budget, and the empty card's header.
Taking v3 literally deletes the feature those four PRs built. That cannot be an inference from a
prototype's omission; a prototype can simply be scoped smaller than the app. **It needs a sentence
from the maintainer either way**, and it is the single highest-cost item in this document.

## 3. Bucket (b) — token names collide at different values

⚠️ **The most dangerous item in this audit, because it fails silently.**

`session-A-tokens.md` instructs a session to write `theme/tokens.ts`. The app's source of truth is
`constants/theme.ts`, and CLAUDE.md says so outright (*"`constants/` is the source of truth for
every number"*). The two use **the same names for different numbers**:

### Radius — every name collides

| name | Session A / v3 | app today | effect if merged |
|---|---|---|---|
| `Radius.sm` | 8 | **12** | every small corner tightens |
| `Radius.md` | 12 | **16** | every card corner tightens 4px |
| `Radius.lg` | 16 | **24** | every large corner tightens 8px |
| `Radius.xl` | 20 | — | new |
| `Radius.full` | 9999 | **999** | harmless |

A session that writes `theme/tokens.ts` and a later one that "consolidates" onto it restyles every
surface in the app, and `tsc` will not say a word — the names all still resolve. Note this also
collides with the **open** `Radius.md` question from the 09-06 audit (16 vs `20-MEASUREMENTS.md`'s
20); v3's answer is a third number, **12**.

### Spacing — nearly compatible, but renamed

App: `xs 4 · sm 8 · smd 12 · md 16 · lg 24 · xl 32 · xxl 48`.
Session A: `xxs 2 · … · xxxl 48` over `2,4,8,12,16,20,24,32,40,48`.

Same values mostly, but **every name shifts by a rung** (`md` would go 16 → 8) and three new rungs
appear (2, 20, 40). The renaming is the destructive half, not the values.

### Type — v3 is a markedly smaller ramp

| role | v3 | app |
|---|---|---|
| card title | **15.5** (`.gc-title`) | **20** (`Type.heading`) |
| card peek | 12.5 | 13 (`FontSize.xs`) |
| row text | 13.5 | 15–17 |
| row sub | 11.5 | 13 |
| screen title | 21 (`.top h3`) | *not verified* — `ScreenScaffold` does not set it from `FontSize`; it goes through the capped header-metrics path (`HEADER_TITLE_LINE_RATIO`). Needs measuring before comparison. |
| nav label | 10.5 | — |

This is not noise; it is a **denser design**, on a 372px frame that is roughly a real phone width.
Adopting it is a legitimate choice, but it is a product decision about density and legibility, and
it interacts with the accessibility work in §4. It should not arrive as a side effect of "extract
the tokens".

### Touch targets — the STOP gate is already answered

`session-B-anatomy.md` halts the session at the Row spec pending a ruling on `.row`/`.grp`
`min-height: 42` vs Android's 48.

**That ruling already exists.** `MIN_TAP_TARGET` has been **48 since 2026-08-08** (Material Design
3, up from 44), `PAD_ROW_MIN_HEIGHT` is 48, and `lib/__tests__/designTokens.test.ts` fails CI on a
bare `44` or `48` at a call site. v3's 42-px row is below the floor the app already enforces. Session
B would stop for a decision that is made — **it should be told 48 and continue.** v3's small
controls (`.gc-btn` 29, `.qbtn` 29, `.add` 26, `.chk` 20) are fine as drawn: the app already has
`HitSlop.base` (10) and `HitSlop.snug` (8) for exactly this, which is what Session B's §6 assumes.

## 4. Bucket (d) — what v3 does not cover

- **Light theme.** v3 is dark-only: `body{background:#080A10}`, and no light values anywhere.
  The app ships both and **CI gates both** — `visual`, `geometry`, `wraps` and `halos` each run
  light and dark. Half the app's rendered surface has no specification here. Session A already
  anticipates this correctly (*"do NOT invent light values"*), so the honest outcome is a dark-only
  token file plus an open question.
- **v3's dark ground is not the app's.** v3 uses a blue-black (`#080A10`, frame `#0A0D15`, cards
  `rgba(19,25,40,.52)`). The app's dark base is flat `#000000` with `#242424` cards — a state
  reached through several dated rulings, most recently the glass work in #675/#677 (*"an ambient
  card paints opaque, so no backdrop colour passes through"*). Adopting v3's ground reverses that
  chain. Conflict, and worth its own decision.
- **No error, loading, offline, or long-content states.** Every list in v3 is 2–5 short Norwegian
  items. The app's `wraps` audit measures 142 wrapped strings at 360px; v3 cannot say what should
  happen to any of them.
- **No settings, onboarding, or editor screens.** The app has `settings`, `onboarding-basics`,
  `onboarding-privacy`, `task-editor`, `health-form`, `medicine-form` and five `design-lab-*`
  screens in the audit set. v3 covers none.

## 5. Bucket (c) — already absorbed, and deliberately deviated from

**The code cites "the mockup" 57 times.** This lineage is not un-started; it is well advanced, with
the deviations written down at the call site. Examples:

- `components/SectionRail.tsx:401` — *"⚠️ `FontSize.xs` (13), not the mockup's 12.5 — a half-pixel
  is not on the type scale"*. This is v3's `.gc-peek` size, already considered and declined.
- `components/SectionRail.tsx:443` — *"marginBottom alone (8, against the mockup's 9)"*.
- `components/Card.tsx:397` — a padding pair reasoned against what the mockup draws.

**This is the strongest evidence that the plan in `HANDOVER.md` is mis-scoped.** It treats the app
as though it has not met this design yet ("the spec is the contract that replaces *look at the
mockup*"). In fact the app has met an earlier draft of it repeatedly, and has recorded ~57 dated
positions. A greenfield token extraction and a from-scratch anatomy spec would re-derive those
positions without seeing the reasons they were rejected — which is precisely how a reversed
decision comes back.

**Recommendation:** Session A and Session B should be reframed from *extract* to *reconcile* —
producing a diff against `constants/theme.ts` and the existing component headers, not a parallel
`theme/` tree.

## 6. Animation — v3's clearest contribution, and it mostly fits

v3's animation section is the best-specified part of the file: durations, curves, and the reason
for each. Mapped against `constants/motion.ts`:

| v3 | duration + curve | app `Duration` | verdict |
|---|---|---|---|
| card expand | 260ms `cubic-bezier(.32,.72,0,1)`, `grid-template-rows: 0fr→1fr`, body fades 200ms @40ms delay, 4px slide | `card: 220` | close; 220 vs 260 is a judgement call |
| card collapse | 220ms ease-out, **content fades out first (120ms), height closes after** | `card: 220` | ✅ duration matches; the *ordering* rule is worth adopting — it names a real artefact ("ellers ser man teksten bli klemt") |
| fullscreen | 360ms, radius 20→26, stack to `scale(.985)` / 60% opacity, scrim `blur(6px)`, **no scale on the card itself** | — | unbuilt as specified |
| back | 300ms, animates toward nearest edge if scrolled out of view | — | unbuilt |
| tab change | 340ms, 12px directional slide, backdrop crossfade 300ms | `ambient: 2400` for the hue crossfade | ⚠️ conflict: 300 vs 2400 is 8×. See note below. |
| row status | 180ms colour only, **no movement** | `control: 150` | close |
| row reorder | FLIP 240ms (v3 admits its own prototype does it instantly) | — | unbuilt; v3 flags it as a known gap in itself |

⚠️ **The tab-crossfade number is worth care.** `Duration.ambient` is 2400ms and that is not an
accident — `scripts/visual-diff.mjs`'s `settle()` was rebuilt on 2026-09-07 (commit 33f3fc5)
specifically because a 2400ms crossfade outlasted the harness's settle budget and made
`task-editor` nondeterministic. Dropping it to 300ms would be a real change to how the app feels
*and* would interact with that fix. Not a token swap.

Note also v3's `grid-template-rows: 0fr → 1fr` has no React Native equivalent — Session B's mapping
table correctly routes it to a Reanimated measured-height transition. That table is sound and
should survive whatever else changes.
