## The one value this session needed pinned, now pinned

**"The card's own hue" (`DESIGN_RULES.md` rule 5) resolves to `getScreenColor(theme,
'shopping').base`** — the same per-screen mechanism `PlanTaskCard.tsx` already uses for `'plans'`
(`components/PlanTaskCard.tsx:627,1237`: `const screenColor = getScreenColor(theme, 'plans')`,
then `rowListStyle({ ..., rail: screenColor.base })`).

This is not a separate registry-declared feature colour. `lib/cardRegistry.ts:167-168` defines the
`hue` field itself as *"Screen hue the card's rail wears — resolved through `lib/screenColor.ts`
at render"* — it is a `ScreenKey`, not a stored colour. The registry entry that owns this content,
`shopLists` (`lib/cardRegistry.ts:296-304`), declares `hue: 'shopping'`. `WeekListCard.tsx:143`
already documents its own card border as `getScreenColor(theme,'shopping').base` — so the card
this row list sits inside is already wearing the resolved value; the row list just needs to reuse
it, not derive a new one.

**Do not introduce a new colour source.** `import { getScreenColor } from '@/lib/screenColor'`,
call `getScreenColor(theme, 'shopping')`, pass `.base` as `rowListStyle`'s `rail` argument.

## Phase B — Converge

For each of the 4 regions in the Phase A table:

1. Import `rowListStyle` from `@/lib/rowList` and `getScreenColor` from `@/lib/screenColor` in
   `components/WeekListCard.tsx` (not yet imported there — confirm).
2. Compute `const screenColor = getScreenColor(theme, 'shopping')` once per render, same pattern
   as `PlanTaskCard.tsx:627`.
3. Replace each `styles.rowsCard` box (and the currently-unboxed purchased region — bring it in
   line with the other three rather than leaving one section flush while the rest are boxed;
   that inconsistency has no design rationale recorded anywhere, unlike `SettingRow`'s grouped-list
   or `MonthlyTableRow`'s flush-table cases which do) with `rowListStyle({ isDark, first, last,
   rail: screenColor.base })` applied per row, `first`/`last` computed from that row's position
   in its own rendered sequence (ungrouped+dish-grouped rows count as one continuous sequence per
   the Phase A table, unless Phase A found the `dishGroup` transparency claim to be false).
4. Delete the now-redundant `styles.rowsCard` definition and the per-row `rowDivider` `<View>`s
   once `rowListStyle()` supplies the equivalent hairline — don't leave both drawing a separator.
5. `theme.good` on the in-cart region and `theme.good`/`theme.accent`'s split across regions both
   go away — every region wears `screenColor.base`, matching rule 5's "the card's own hue," not a
   semantic colour chosen per section.

**Do not**, in this session:
- Touch `MedicineSurface.tsx` or `MonthlyTableRow.tsx` — both remain open per
  `DECISIONS_OPEN.md`'s amended option C, and neither is this session's subject.
- Touch `TaskCard.tsx`, `TodoSurface.tsx`, or `NoteRow.tsx`/`NotesSurface.tsx` — those are the
  "separate floating cards" surfaces the still-open A/B/C decision governs; this session's scope
  is the one surface that's already unambiguous.
- Change `ShoppingRow.tsx`'s own internals beyond what's needed to sit correctly inside a
  `rowListStyle()`-boxed row (e.g., if it currently assumes it owns its own background/border,
  that assumption may need adjusting — but its checkbox/swipe/content logic is out of scope).
